### 5.1 Why both execution orders fail unchanged

M5 first: any genuine M5-only state-changing operation makes N>C. The next new
direct acquire or completion validates the base at N but asks the M4 counter
for transition.expected_revision=N. The counter is still C; it rejects.

Direct first: native direct work can advance N=C until M5-only work starts.
If the last direct completion occurs while M5 counters are nonzero, its correct
outer projection commits SP, not SCOMP. Subsequent M5 work makes N>C and its
last C2 still leaves SP. Completed direct history excludes R33/J33. Legacy
seal both lacks the required complete header and enforces counter equality.

Interleaving is no escape: the first M5-only increment creates the gap. A lease
obtained before that increment does not let its later direct completion use a
stale base revision. Scheduling every direct operation before all M5 work still
has the direct-first terminal gap. Nonempty REPLACE cannot omit the M5 roots.
These are deductions from the actual guards, not timings or a new live result.
